# Session note — 2026-05-08 — ash edit verb

## Task
Implement `ash edit` — structured in-place file mutation to complement `ash read`/`ash write`.

## Verbs used
- `ash find`, `ash read`, `ash grep` for exploration
- `ash report` for ledger summary
- `ash write` attempted for session note (shell quoting issue with multiline content; fell back to harness Write)

## Design decisions
- **Two modes, one verb**: `old_string`/`new_string` (string replacement) and `range`/`new_content` (line-range replacement), discriminated by which required arg is present. No `--mode` flag needed — mode is self-evident from args.
- **`ambiguous` error on multi-match**: if `old_string` appears N>1 times and `replace_all=false`, error rather than silently replacing the first occurrence. Agents should fail loudly on ambiguous edits.
- **Atomic write**: temp-file + rename, same pattern as `ash write`. Original file permissions are preserved via `os.Chmod`.
- **Line-range clamping**: `end > nLines` is clamped to `nLines` rather than erroring, matching `ash read` range behavior.
- **Trailing newline normalization**: if `new_content` is provided without a trailing newline, one is appended automatically.

## Friction / workarounds
- Harness Edit tool required a prior native Read (internal guard). `ash edit` has no such requirement — agents can call it directly. This removes one class of unnecessary harness Read calls.
- `ash write` with multiline `--content` containing single-quote characters fails in zsh due to shell quoting. Needs a quoting helper or here-doc support in the CLI. Filed as a note for a future ship.
- Harness Read still needed to satisfy the Edit/Write "file has been read" guard before the hook was updated. Now that `ash edit` is live, the guard is moot for edit workflows.

## Hook update
