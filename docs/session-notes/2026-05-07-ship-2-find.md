# 2026-05-07 — Ship 2: `ash find`

## Task

Build `ash find`: list paths under a starting directory, with doublestar glob, type filter, depth cap, exclude pattern, hidden-dir skip, and bounded output. Wire it through the daemon and client. First verb where the recursive-development thesis has real traction — multi-file path lookup is one of the operations agents do most often.

## Verbs used

`ash find` itself, multiple shapes (default glob, `**/*.go`, `**/*.md`, `--max_depth 1`, `--exclude bin/**`, `--limit 5` to force truncation). `ash read` was not exercised this round; the harness Read/Write/Edit and bash were the development substrate.

## Friction

Three friction points worth recording:

1. **My own test fixtures fought my own design.** The verb's path-form-mirrors-input rule (relative-in → relative-out, absolute-in → absolute-out) is correct and matches Unix `find`. But `t.TempDir()` returns absolute paths, so my first test pass had assertions like `contains(got, "src/deep")` against results like `/var/folders/.../src/deep`. Five tests failed in a row before I caught it. The fix was to stripping the root in the test helper, not changing the verb. Lesson: when output form depends on input form, write the test helper that handles both *first*, before any assertions. The test was about the right thing — I just compared the wrong column.

2. **`bin/` shows up in find results.** Gitignore is a git concept, not a filesystem concept. `find` correctly walks the binaries because they're real files on disk. But every `ash find --path .` in this repo includes ~28 MB of compiled binaries unless I pass `--exclude 'bin/**'`. That gets old fast. Self-hosting cost: an extra flag on most invocations.

3. **`docs/.gitkeep` lingered for two ships.** I deleted `docs/session-notes/.gitkeep` in ship 1 but never cleaned up the parent `docs/.gitkeep`, and it was invisible in `git status` (already committed in Phase 0). It only surfaced because `ash find --max_depth 1` listed it. Cleaned up this round. Lesson: dogfooding actually catches invisible mess in the repo. The instrumentation thesis works.

## Workarounds

None for verb correctness — all bugs were caught in test or fixed during smoke-testing.

For `bin/` noise, pass `--exclude 'bin/**'` until a better default exists.

## Suggestions

In rough priority order:

- **Gitignore-aware mode for `find`.** A `--respect_gitignore` flag (or a default-on behavior with a way to disable) that reads `.gitignore` and treats matched paths as excluded. Would silence `bin/`, `.ash/` would already be skipped via hidden-dir rule. Implementation: `github.com/sabhiram/go-gitignore` is a pure-Go reader, fits the no-CGO constraint. Add to ship 3 or ship 4.

- **Default-exclude common dumpsters.** Even before gitignore-aware mode lands, default-excluding `node_modules/`, `vendor/`, `target/`, `dist/`, and `bin/` would eliminate the most common token disasters. The cost is one violation of the "one canonical way" principle (implicit behavior), but the benefit is enormous. Maybe gate on `--respect_dumpsters=false` to keep it explicit.

- **Pre-warm tiktoken.** Still on the list from ship 1. First call after fresh daemon start is 2-3x slower than warm calls because of lazy BPE init. `ash find` with 13 results showed exec=670µs cold vs 295µs warm. Would land in `ledger.NewCounter`.

- **Verb dispatch registry.** The daemon's `switch req.Verb` and the client's `switch verb` are both two-case now (read, find). Ship 3's `grep` makes it three. At three, refactor into a `map[string]verbHandler` so adding new verbs is an import + one-line registration. Don't refactor at two; refactor at three when the pattern is clear.

- **Loud ledger failures (already shipped) needs an end-to-end test.** The unit test in `ledger_test.go` proves Record errors out on a closed DB. The wire round-trip test proves the field survives encode/decode. But there's no test that asserts the daemon, in the field, sets `LedgerError` correctly when Record fails. A small integration test with an injected broken ledger would close the loop. Ship 3 nice-to-have.

- **`--format json` on the client.** Still pending from ship 1.

- **Truncation hint accuracy.** Today the hint says "raise --limit (max 4096)". For a real walk that would genuinely return >4096 results, raising `--limit` doesn't help — the ceiling itself is the issue. The hint should detect that case and instead suggest narrowing.

## Instrumentation

Five `find` calls in `.ash/ledger.db` (today's session, post-rebuild):

| call | shape | tokens_in | tokens_out | bytes_in | bytes_out | latency_exec_us |
|---|---|---|---|---|---|---|
| 1 | `--type file --glob '**/*.go'` (cold) | 13 | 252 | 62 | 971 | 670 |
| 2 | `--max_depth 1` | 10 | 289 | 51 | 970 | 368 |
| 3 | `--type file --glob '**/*.md'` | 13 | 81 | 62 | 246 | 295 |
| 4 | `--type file --exclude 'bin/**'` (21 results) | 12 | 375 | 64 | 1435 | 1529 |
| 5 | `--type file --limit 5` (TRUNCATED) | 12 | 131 | 57 | 450 | 87 |

Observations:

- **Token-out per record averages ~17 tokens** for the canonical pretty form (`F <size> <date> <path>`). For 21 results that's 375 tokens. A bash `find . -type f` on the same set would emit just paths and roughly the same content — without the type marker, size, date — at maybe 60% of the tokens. So our format is *more expensive per record* than bare paths, but trades that for type, size, and date carried in-line. Whether that's the right tradeoff depends on what agents actually need. Need to ask the next agent.
- **Cold-start tax persists.** 670µs cold (call 1) vs 87µs warm-and-narrow (call 5). The first-call penalty is still tiktoken lazy-init.
- **Walk dominates exec for unfiltered queries.** Call 4 at 1529µs walked 21 file results plus dir entries; the actual work was 99% filesystem, 1% glob/filter logic. As result counts grow, this becomes the bottleneck. Ripgrep-style parallel walks are the eventual answer; not for this ship.
- **Hidden-dir skip is doing real work.** Without it, `.git/` alone in this repo would have added hundreds of result rows of pure noise.
